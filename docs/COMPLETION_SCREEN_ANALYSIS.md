## 🎯 研究目标

让 Monster Hunter World 在结算画面时，截图也使用全屏分辨率（16:10 或其他），而不是被强制裁剪为 16:9。

---

## 🔧 前置准备

### 1. 安装依赖
```bash
pip install capstone pefile
```

### 2. 配置 MHW16x10Fix.ini
```ini
[Fix]
Enabled=true
AutoDetectAspect=true
Width=1280
Height=800
RemoveLetterbox=true

[Loader]
ChainLoad=
ForwardDirectInput8Create=true

[Debug]
EnableLog=true
TraceCompletionLayout=true  ; 启用追踪！
```

### 3. 游戏设置
- 使用 **DX12** 模式
- 分辨率设置为你的全屏分辨率（如 1280x800）
- 无边框窗口或全屏模式

## 🚀 工作流程

### 阶段 1：数据收集

#### 步骤 1：启动游戏并等待
1. 启动游戏
2. 进入主菜单后，**等待 60 秒**（让追踪计时器启动）
3. 不要按任何键，保持在菜单

#### 步骤 2：进入结算画面
1. 开始一个任务（推荐训练区任务，快速完成）
2. 完成任务，进入结算画面
3. **暂停在结算画面**（不要继续）
4. 按截图键（ Steam F12 或游戏内置截图）

#### 步骤 3：运行扫描脚本
在游戏暂停时，打开另一个命令行窗口：
```bash
cd e:\repository\MHW16x10Fix
python work\scan_completion_enhanced.py
```

保存输出！

#### 步骤 4：获取日志文件
找到 `MHW16x10Fix.log`，通常在游戏目录或构建目录。

---

### 阶段 2：分析数据

#### 分析日志
```bash
python work\analyze_trace_log.py <path_to_log>
```

这会：
- 统计所有事件
- 找出 16:9 相关的事件
- 列出需要反汇编的 RVA

#### 反汇编感兴趣的代码
使用上面脚本输出的 PID 和 Image Base：
```bash
python work\analyze_disassembly.py <PID> <IMAGE_BASE> <RVA1> <RVA2> ...
```

当找到可能的目标后：

增强版扫描脚本。

**功能：**

- 扫描整个内存中的 16:9 尺寸

**使用时机：** 游戏暂停在结算画面时。

  Line 1234: DX12 texture created: 1280x720 ...

```

**功能：**
- 查找函数边界

**使用方法：**

python work\analyze_disassembly.py 12345 0x7FF600000000 0x12345 0x23456

## 🛠️ 修复策略

### 策略 A：修改渲染管理器尺寸
**假设：** 渲染管理器中有存储结算画面目标尺寸的字段。

**方法：**
1. 找到这些字段的偏移
2. 在 `native_aspect_worker` 或 `request_native_aspect_mode` 中修改它们
3. 或者定期检查并覆盖

---

### 策略 B：钩子视口/裁剪设置
**假设：** 游戏在绘制结算画面时显式设置 16:9 视口。

**方法：**
在 `rs_set_viewports_hook` 和 `rs_set_scissor_rects_hook` 中：
1. 检测是否在结算画面（通过调用栈或其他标志）
2. 如果是 16:9 尺寸，修改为全屏尺寸

---

### 策略 C：钩子纹理创建
**假设：** 游戏创建 16:9 的渲染目标作为截图目标。

**方法：**
在 `create_committed_resource_hook` 中：
1. 检测是否创建 16:9 渲染目标
2. 检查调用栈判断是否是截图相关
3. 修改创建的高度为全屏高度

---

### 策略 D：钩子纹理复制
**假设：** 游戏从 16:9 渲染目标复制到最终输出。

**方法：**
在 `copy_texture_region_hook` 等中：
1. 检测从 16:9 到其他尺寸的复制
2. 修改源区域或目标位置

## ⭐ 2026-08-06 实测：结算背景的真凶是两处未同步的 16:9 字段

在 1920x1200 / DX12 / 停在结算画面时，直接读运行中进程（`work/read_live_layout.py`）
并全结构扫描 512 KB（`work/sweep_stale_169.py`），结果如下。

### native aspect fix 本身完全生效

```
content_size (+0x198/+0x19C) = 1920x1200   aspect=1.600000
output_dims  (+0x1F448)      = 1920x1200   aspect=1.600000
active_mode = 0, requested_mode = 0
+0x7B444 (float)             = 1.600000
```

**「applied 日志没打印」只是日志分支问题，不是功能没跑。**
曾据此误判为 content size 停在 16:9，已推翻。

### 只有两个 dword 仍等于 1080

| 偏移 | 值（native aspect 生效后） | 状态 |
|------|------|------|
| +0x190 / +0x194 | 1920x1200 | ✅ 跟随 |
| +0x198 / +0x19C | 1920x1200 | ✅ content_size |
| **+0x1A0 / +0x1A4** | **1920x1080** | ❌ **未同步** |
| **+0x210 / +0x214** | **1920x1080** | ❌ **未同步** |
| +0x774, +0x3304, +0x5E04, +0x5E14, +0x8914, +0xB414, +0xDF14, +0x1F448 | 1920x1200 | ✅ 跟随 |

512 KB 全扫：无硬编码 1.7778 浮点，无其他漏网的 16:9 值。
`1200 - 1080 = 120px`，与「背景没铺满」的观感一致。

结算 UI 的 scissor 为 `left=138, top=83, right=1304, bottom=1200`（高 1117），
即 **UI 锚点用全高、背景用 1080**，两者错开。

### 活体写入实验（`work/poke_stale_169.py`）

```
+0x1A4: 1080 -> 1200  OK   1.5s 后仍为 1200 (held)
+0x214: 1080 -> 1200  OK   1.5s 后仍为 1200 (held)
```

游戏未崩溃，`Responding=True`，**引擎不会写回** —— 这两个字段是「写一次就认」
的状态量，不是每帧重算，因此适合做成正式修复。

### 已排除的假设：B / C / D 全灭

结算画面追踪窗口（draws / RT / copy 全部 hook 成功）显示：

- 所有 draw 的 viewport/scissor 均为全尺寸，**不存在 16:9 视口** → 策略 B 排除
- 绑定的 render target 全为全尺寸，**无 16:9 RT** → 策略 C 排除
- **完全没有** CopyTextureRegion / CopyResource / ResolveSubresource 事件 → 策略 D 排除

背景是以 UI 几何（顶点坐标）画在全尺寸 RT 上的，几何本身按 16:9 算出来 ——
**策略 A 成立**。

### 相关脚本

- `work/read_live_layout.py <pid> <base_hex>` —— 读关键字段 + 邻域 sweep
- `work/sweep_stale_169.py <pid> <base_hex> <w> <h>` —— 全结构找残留 16:9
- `work/poke_stale_169.py <pid> <base_hex> <w> <h> [restore]` —— 活体写入验证

取 pid / base：

```powershell
$p = Get-Process MonsterHunterWorld
"pid=$($p.Id) base=0x{0:X}" -f $p.MainModule.BaseAddress.ToInt64()
```

### ⚠️ 非标分辨率会干扰判断

此前用的是 `Resolution=2240x1463`（aspect 1.531，既非 16:10 也非 16:9），
已改回 `1920x1200`。排查布局问题**务必先用整数标准比例**。
备份：`graphics_option.ini.bak-2240x1463`。

### ⚠️ 读 10 MB 日志的坑

- 游戏运行中日志被独占，`[System.IO.File]::ReadAllLines` 直接抛
  `IOException: 正由另一进程使用` —— 必须用
  `FileStream` + `FileShare::ReadWrite` 打开。
- 用 `$arr += $line` 逐行追加在十几万行上是 O(n²)，会挂死。
  改用 `System.Collections.Generic.List[string]` 的 `.Add()`。
- 现成脚本：`workspace/tmp/read_mhw_log.ps1`（切出最后一个 session 并过滤噪声行）。

## 🔧 HUD 错位的修复思路（2026-08-06 记录）

> ### ⚠️ 本节前提已于同日撤回，请先读这段
>
> 「HUD 错位」这个观察**是误读，不成立**。
>
> 用户随后纠正：**游戏本来就有两套 R/F 提示** —— 一套在物品栏下方靠右，
> 点了之后会在画面中间再出现一个。所谓「R/F 从中间跑到右边」看到的是
> 游戏原生行为，**没有任何证据表明 HUD 被改动过**。
>
> 连带撤回的还有一条推论：因为「还原后 R/F 没回到中间」，
> 曾据此断定「HUD 布局一次性算完并缓存」。
> 该前提既然不成立，**这个结论也不成立**。
>
> 因此下面「关键推论」小节里
> 「只改高度却横向位移 → 该字段是 UI 参考分辨率」的论证
> **失去了唯一的证据支撑**。字段真实用途**目前未知**。
>
> **仍然成立的部分**（这些不依赖那个误读）：
>
> - `+0x1A0/+0x1A4`、`+0x210/+0x214` 是 512 KB 里唯一残留 1080 的字段
> - 写成 1200 **确实让背景发生了变化**（方向对了）
> - 引擎不会把它写回 1080
> - 策略 B / C / D 的排除证据（viewport、RT、copy）不受影响
>
> 下面的五条候选方案**保留**，因为它们本身仍是合理的探索方向；
> 但候选 1（Ultrawide UI Layout）的优先级理由从
> 「修 HUD 错位」改为「排查非 16:9 布局是否本就有官方处理」。
>
> **教训**：把游戏原生 UI 行为误当成 mod 副作用，
> 白绕了一大圈还污染了后续推理。
> 观察到「异常」时，先确认没开 mod 时是不是也这样。

### 现象

把 `+0x1A4` / `+0x214` 从 1080 改成 1200 后：

- 背景**有变化**（说明这条线是对的）
- ~~但 **HUD 错位**：R/F 提示从画面中间跑到了右边~~
  → **已撤回，见本节开头**：那是游戏原生的两套 R/F 提示，不是 mod 造成的

### ~~关键推论：这不是尺寸字段，是「UI 参考分辨率」~~ （证据已撤回）

> 以下论证依赖「只改高度却横向位移」这个已被推翻的观察，**仅作存档**。
> 字段真实用途未知，需要重新做受控实验。

**我只改了高度，HUD 却横向位移** —— 这是最重要的一条证据。
纯尺寸字段不会有这种表现。合理解释：引擎用
`+0x1A0/+0x1A4` 算宽高比，高度从 1080 变 1200 →
aspect 从 1.7778 掉到 1.6 → 居中类元素的水平锚点被重算 → 整体右移。

即 `1920x1080` 在这里的角色是**UI 虚拟画布 / 参考分辨率**，
HUD 坐标先在这套画布里算，再映射到实际输出。改了画布高度，
横向映射系数跟着变，于是横向也歪。

所以**「把 1080 改成 1200」很可能不是正解**。正解应该是：
让背景用全高，同时让 HUD 的映射保持原来的横向系数。

### 候选方案（按优先级）

#### 候选 1：游戏自带的 Ultrawide UI 选项 ⭐ 优先试，零成本

`graphics_option.ini` 里存在：

```ini
Ultrawide Mode UI Layout=0
```

MHW **原生就有**非 16:9 的 UI 布局模式。这说明引擎内部已经有一套
「输出比例 ≠ 16:9 时如何摆 HUD」的逻辑，不需要我们自己造。

先试把它改成 `1`（或枚举其他值）再配合 `+0x1A4=1200`，
看 HUD 是否自动回到正确锚点。**如果这条通了，整个修复会干净得多。**

先摸清取值范围：改前备份，逐值试 0/1/2。

#### 候选 2：只改背景那条线，不碰 UI 参考分辨率

需要先做差分实验分清 `+0x1A4` 和 `+0x214` 各管什么
（`work/poke_field.py` 已支持逐字段写）。

如果其中一个只影响背景、另一个只影响 HUD，那直接只改背景那个即可，
HUD 完全不动 —— 最理想的结果。

#### 候选 3：改宽度补偿，保持 aspect 不变

如果 HUD 位移纯粹由 aspect 变化引起，那么在抬高度的同时
**等比抬宽度**，让 `+0x1A0/+0x1A4` 的比值保持 1.7778：

```
height 1080 -> 1200  (x1.1111)
width  1920 -> 2133  (x1.1111)
```

HUD 锚点系数不变，但画布变大 → 背景可能跟着铺满。
副作用：HUD 整体可能缩放或留边，需实测。

#### 候选 4：定位读取方,在指令级分流

用 `work/find_runtime_field_accesses.py` / `disassemble_runtime_rvas.py`
找出所有读 `+0x1A0`/`+0x1A4`/`+0x210`/`+0x214` 的指令，
区分「背景几何计算」与「HUD 锚点计算」两类调用点，
只对背景那条路径喂全高值（改指令或改中间变量），HUD 路径保持 1080。

最精确，但工作量最大。作为前三条都失败时的兜底。

#### 候选 5：接受 HUD 偏移，反向补偿

如果 HUD 位移量是固定可预测的（比如恒定右移 N px），
可以在 HUD 那条线上加一个反向偏移量抵消。
**不推荐** —— 属于治标，换分辨率就得重新调。

### 下一步该测什么

**先决条件：每次实验都必须有对照组。** 判断任何「异常」之前，
先确认关掉覆盖（四个值全 0）时是不是也长这样 ——
上一轮就是因为缺这一步，把游戏原生的双份 R/F 提示误判成 mod 副作用。

实验现在**全部通过 INI 做**，改完重启游戏即可，不用重编译：

```ini
[Experimental]
UiReferenceWidth=0        ; +0x1A0
UiReferenceHeight=0       ; +0x1A4
SecondaryLayoutWidth=0    ; +0x210
SecondaryLayoutHeight=0   ; +0x214
```

1. **对照组**：四个全 0，进结算，记下背景的确切样子（截图最好）
2. `UiReferenceHeight=1200` —— 只动这一个，只看背景
3. `SecondaryLayoutHeight=1200` —— 只动第二组
4. `UiReferenceWidth=2133` + `UiReferenceHeight=1200` —— 锁 16:9 比值
5. 四个全 0，改 `graphics_option.ini` 的 `Ultrawide Mode UI Layout=1`

要填的表：

| +0x1A0/+0x1A4 | +0x210/+0x214 | 背景 | HUD（对照后再判断） |
|---|---|---|---|
| 原值 | 原值 | 未铺满 | 基准 |
| 1920x1200 | 原值 | ? | ? |
| 原值 | 1920x1200 | ? | ? |
| 2133x1200 | 原值 | ? | ? |

> ⚠️ **不要再用外部 poke 脚本下结论。** 进结算后才写入，看到的可能
> 既不是「生效」也不是「无效」。脚本只留作读字段/快速侦察用。
